# pipes/ — cross-stream inboxes (pilot v0.1, adopted by the PI 26 Oct 2026)

One inbox per stream: `pipes/<STREAM>/`. An item is one file, `YYYYMMDD-<FROM>-<slug>.md`, with the front matter below and a short body. `pipes/<STREAM>/INDEX.md` is generated by `tools/pipes_index.py` and never hand-edited. Stream keys are those of Programme §6.1 / `BASELINE.md`: METH, PROG, OFN, RRF, LEGACY, PREL, NUMGEN, DYAD, TRIAD, GEN, UVM, RECOG, DZT, TDRG, AZ, RER, FMS, ER2B, ATLAS.

## What an item is

A **request, offer, finding, question or notice** from one stream (or the atlas) to another. It carries no scientific authority: the producer stays the owner of its result; the receiver alone decides what to do with the item, in its own text and ledgers. Nothing is routed through the PI (PI decision, 26 Oct 2026): the co-owners of the receiving stream read their inbox at the checkpoints below and decide autonomously. A pipe item is never "adopted use" by itself — adopted use is asserted only by the receiver's Import Ledger row (by RID, at the producer edition) or release record.

## Checkpoints — when a stream reads its inbox

1. At the start of an owner pass or advisory cycle on that stream.
2. Before freezing a stage-1 intermediate and before a release record is finalised.
3. Whenever the stream's own work is blocked on an item it filed elsewhere (`blocks`), to see whether the receiver has answered.
Outside these points nothing is expected of the receiver.

## Front matter

```
from: NUMGEN                      # stream key; sessions sign with their stream, never with a model name
to: TDRG
date: 2026-10-26
kind: request | offer | finding | question | notice
object: TDRG-ORIENT (TDRG §6); NUMGEN v1.20.8 §6.6   # RIDs / sections, at the tags below
tags: [tdrg-v2.12.13, numgen-v1.20.8]               # git tags the object is read at
state: open                       # open → acknowledged → dispositioned → closed; changed by the RECEIVER only
blocks: NUMGEN C7C-M4 realization campaign (§2 item 1)   # optional; name the RID/OPEN/campaign held, or omit
disposition:                      # receiver: date · verdict (accept / accept with change / reject / defer) · pointer to its record or ledger row
```

Body: one to ten lines — the finding or expectation, the owner lines quoted or cited, and what the sender needs (a decision, a RID, a scope sentence, nothing).

## States

`open` — filed; nothing expected yet. `acknowledged` — the receiver has read it (its session or record says so). `dispositioned` — the receiver has recorded a verdict in `disposition` with a pointer. `closed` — the verdict is carried by the receiver's adopted edition (Import Ledger row, release record, or an explicit "no action" record); the pointer in `disposition` says where. A sender may add a line to the body (dated) but never changes `state`.

## Rules

- Anyone with repository access files an item on a branch and opens a PR; the receiver's co-owners change `state`/`disposition` the same way.
- One item, one question. Science lives in the DSNs and records; the item cites them by tag, section and RID. No hash, RID or approval is invented; "not available" is written as such.
- `blocks` should name the receiver-side or sender-side identifier that waits (RID, OPEN key, campaign name), so the atlas can show which open item holds which work.
- `tools/pipes_index.py --check` validates every item (fields, states, stream keys, tags exist) and rebuilds the indexes; it runs in the PR that files or changes an item.
- The atlas reads pipes as records: open items become `~` edges or diagnostics; closed items retire them. The Programme's §7.2 interface register remains the owner-declared truth; pipes are the queue in front of it.

This pilot changes no Methodology text. `CONVENTIONS.md` §7 is amended in the same PR to point here; a Methodology clause follows after one cycle if the pilot proves useful (`records/methodology/`).
